Who the patient is, across every system that knows them.

FerroPIX is the Master Patient Index of the FerroHEALTH family, in pure Rust. Each hospital, practice and national register issues its own identifier for the same person. FerroPIX holds the cross-reference between them in PostgreSQL, answers for it over the IHE profiles your systems already speak, and mints the pseudonyms a clinical store names a patient by, so identifying data stays outside the clinical record.

Run the quickstart What FerroPIX is

A server image, an operator console image and a Helm chart on GHCR, built at SLSA Build Level 3, and the two identity crates on crates.io.

What it answers

One cross-reference behind every face

A feed over FHIR and a feed over HL7 v2 of the same patient land in one person, and every query reads the same store. Each transaction follows the IHE ITI Technical Framework and its implementation guide, on HL7 FHIR R4, and the book cites the section behind every answer.

PIXm 3.1.0

The PIXm Manager

ITI-83 answers which identifiers the other domains hold for a patient, by GET or by a posted Parameters body that keeps the identifier out of every URL. ITI-104 lets each domain's one Source feed, revise, merge and remove.

PDQm 3.2.0

The PDQm Supplier

ITI-78 finds patients by demographics and identifiers, with paging and the domain filter. ITI-119 $match scores the patient you describe and grades each answer certain, probable or possible.

PMIR 1.6.0

The PMIR Registry

Receives the master identity feed (ITI-93), takes subscriptions (ITI-94), and sends every committed change to each subscriber, in order, from an outbox written in the change's own transaction.

ITI TF-2

HL7 v2 PIX and PDQ

An MLLP listener for the identity feed (ITI-8), the PIX query (ITI-9) and the demographics query (ITI-21), and update notifications (ITI-10) to the consumers you name, on FerroBRIDGE's v2 parser.

ITI-55

The XCPD Responding Gateway

Another community asks whether yours knows a patient, by a shared identifier or by demographics, and gets the patient's identifiers in your domains, on the same exchange or asynchronously.

Pseudonyms and the BSN

Identifying data stays out

One pseudonym per patient and pseudonymisation domain, read only by that domain's consumer. The BSN is checked by the eleven-proof, and every identifier of a sensitive domain is sealed at rest and found by a keyed hash.

The operator console

A data steward decides what the scorer is unsure of

An identifier in an authoritative domain links two records on its own, a probabilistic scorer grades the rest, and the pairs it is unsure of wait in a review queue. The console is where a steward compares them, links, merges and unmerges with a reason, and every reveal of an identifier is an audited disclosure.

Run it

From a laptop to a Kubernetes cluster

The server is one static binary on a distroless base, beside PostgreSQL and the authorization server you already run. The console is its own image and keeps no patient data.

Compose

The quickstart

docker compose up --wait from a checkout starts the server, PostgreSQL and a development issuer; the console profile adds the console. Then feed a patient and ask for it.

OCI images

The container images

ghcr.io/ferrohealth/ferropix and ghcr.io/ferrohealth/ferropix-console, for amd64 and arm64, each with SLSA provenance and an SBOM you verify before you run it.

Helm

The chart

oci://ghcr.io/ferrohealth/charts/ferropix runs the server and the console under the Restricted Pod Security Standard, with both images pinned by the digests the release scanned.

In the family

The one product that owns patient identity

The FerroHEALTH products reach each other only over published protocols. FerroPIX is where they ask who a patient is.

FerroEHR

With its PIXm subject index, the openEHR clinical data repository finds a patient's EHR through FerroPIX: the EHR_STATUS names the patient by the pseudonym FerroPIX minted for the clinical domain.

FerroFED

The federation gateway resolves the patients of a cross-site query through a PIXm Manager, and takes both identity crates from crates.io.

FerroBRIDGE and FerroTERM

The HL7 v2 face reads messages with FerroBRIDGE's parser and MLLP codec, and translates every v2 table value on a FHIR terminology server such as FerroTERM.

Building a client in Rust? Each IHE profile is a feature of ihe-iti, and each Dutch Generic Function a feature of nl-generic-functions, none on by default: 

cargo add ihe-iti --no-default-features -F pixm
