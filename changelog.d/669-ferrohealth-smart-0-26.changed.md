- Breaking: the server keeps an overload bound always: `server.max_concurrent_requests` is 256 by default, where unset left the server unbounded, so past 256 requests in flight a request is answered `503` with `Retry-After` and the health routes are never refused. A deployment that relied on no bound sets the ceiling it wants (FerroHEALTH/FerroEHR#5743).
- Breaking for crate users: `ihe-iti` 0.12.0 requires `ferrohealth-smart` 0.26 and `ihe-atna` 0.21, and `nl-generic-functions` 0.12.0 requires `ferrohealth-smart` 0.26 and `ihe-iti` 0.12. Their public API carries the types of those crates (the outbound client, the endpoint table and the audit user), so a consumer moves to the same lines. The server and the console move to `ferrohealth-smart` 0.26, `ferrohealth-server` 0.10, `ferrohealth-session` 0.21, `ihe-atna` 0.21, `ferrobridge-term` 0.11 and `ferrobridge-hl7v2` 0.16, so one smart, one server and one telemetry link.
